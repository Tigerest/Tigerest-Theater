# 首页／媒体夹／详情转场触发延迟优化 · 2026-10-10

基线为 upstream `v2.5.2`（`977a480`）。本轮只改转场的准备方式，海报飞行、遮罩、首页飞出及入场的关键帧和时长保持不变。

## 2.5.2 点击卡顿的来源

1. **命中缓存仍重排整页副本。** 媒体夹和详情页的预热快照是整页 DOM 副本（含复制进 shadow 的全部样式表）。点击时它被移出隐藏容器、放入遮罩层，再同步恢复滚动位置；移动节点会丢弃布局，整棵副本在首帧前重新计算样式和布局。海报转场里这份副本透明度为 0，并不可见。
2. **未命中时点击同步复制整页。** 缓存失效后（滚动、悬停改动 DOM、轮播、图片加载）约 0.3s 内点击，在点击任务里同步克隆页面和样式表。
3. **首页悬停后马上点击，导航被入场动画拖住。** 悬停切换作品会重播标题／简介入场，预热任务要等这些动画结束（约 1.3s）才生成位图；点击会等待这个任务，导航被推迟约 0.7s。
4. **海报起飞前再复制一次目标页。** 目标海报落位后，同步复制新页面 DOM 作为模糊背景，并对整页再做一次采集和图片解码。
5. 首页每 6.5s 轮播一次，每次都重建整页快照。

## 改动

- **海报转场（首页→详情、媒体夹→详情、详情→媒体夹）不再复制 DOM。** 命中时只用预热的 240px 模糊位图。未命中时立即在实时页面上加 `backdrop-filter: blur(7px)` 镜片层；位图就绪后再淡入不透明遮罩并开始导航。没有 Worker/OffscreenCanvas 或位图失败时，才回退到原来的模糊 DOM 副本。
- **预热还在等入场动画时，点击直接中止它**，按当前画面采集；已进入采集阶段的任务照常等待。
- **目标页用同一镜片实时模糊。** 遮罩在 16%→48% 淡出，等价于原目标副本淡入；镜片在 70%→100% 淡出，等价于原遮罩淡出。不再复制目标页，也不再为目标页解码图片。
- **首页→媒体夹的飞出直接作用于实时的导航、轮播和舞台元素**，关键帧不变；遮罩在最后 42% 由透明变为 `#0b0d12`。动画在任务结束时取消。
- **返回首页仍需要清晰副本。** 预热副本改为原地提升为遮罩层，不再移动节点和恢复滚动。首页本身不再生成副本；其他页面在位图就绪后的空闲回调中生成。
- 背景采集按子树跳过 Emby 隐藏视图和动效层；移除已不使用的整页节点映射。

## Linux 客户端实测（QtWebEngine 6.4）

按 `dev/linux/build.sh` 的方式在 Ubuntu 24.04 上构建了真实客户端 `tigerest-theater`，使用系统自带的 Qt 6.4.2，即 QtWebEngine 6.4（Chromium 102）；正式包用的是 Qt 6.9。客户端在 Xvfb 中运行，没有 GPU，并使用临时隔离配置。

- `test_home_motion_ui`、`test_home_motion_cache_ui`、`test_home_gallery_ui`、`test_home_touch_ui` 以 `--webengine` 模式在客户端内运行，全部通过。
- 用同一环境分别编译 2.5.2 脚本和本次脚本，跑重型夹具，每项 3 次。点击时同步执行的 JS 耗时（即阻塞输入的部分）：首页→详情由 6.8–15.2ms 降到 2.5–6.4ms；媒体夹→详情由 94–112ms 降到 12–21ms；详情→媒体夹由 80–127ms 降到 6–39ms。
- 该环境下两版的单次转场都要 10–22 秒，期间有 3–5 秒没有一帧。CPU profile 中 JS 约占 1 秒，其余是 QtWebEngine 6.4 纯软件渲染的原生样式／布局／绘制时间，所以整体耗时和帧间隔不作为结论。几次未命中缓存的测量中位图生成超过 2 秒上限，按设计回退到 DOM 副本，回退路径工作正常。
- 夹具海报原为 600×900 的 SVG，在这个引擎下栅格化会让转场停顿约 7–11 秒，因此基准改用 Node 生成的 300×450 PNG，更接近 Emby 的 JPEG 海报。

客户端无法连接 `http://nas.tigerest.top:8095`：容器出站只支持 HTTPS，而服务器只有明文 HTTP。因此没有用真实 Emby 页面和账号测试。

新增的“入场动画不推迟导航”和“首页→媒体夹不复制”两条断言在 2.5.2 代码上失败（导航 2129ms；点击帧仍有副本），改动后通过。截图另外确认了冷点击镜片会模糊实时旧页面、目标页镜片会模糊实时新页面，以及导航前由不透明位图遮盖。

## 第二轮优化（2026-10-11）

点击当下的卡顿解决后，主要开销转到整页 DOM 副本上：返回首页未命中缓存、首页→媒体夹的放大入场、空闲预热快照，以及没有位图时的回退。另一部分开销在路由完成到海报起飞之间的等待。对返回首页时的副本逐阶段打点：逐节点处理占 14–79ms，克隆占 7–30ms，复制样式表只有 1–3ms；挂载后的首帧随副本节点数增长。

- **整页副本：**
  - 克隆时直接跳过 Emby 隐藏的缓存视图和动效层。
  - 原来对每个节点写入 `animation/transition:none!important`，改为副本内一条 `:is(*,#t×10)` 规则：它的优先级相当于十个 ID，仍能压过样式表里带 `!important` 的入场动画。
  - 只有正在动画、过渡、悬停或聚焦的节点才抄写计算后的 opacity/transform/filter，其余节点与样式表一致。
  - `.itemsContainer` 里完全在视口外的卡片换成不可见的占位，保留未取整的原尺寸，可见卡片位置不变。
- **目标海报图片与飞行并行加载。** 海报副本会一直盖住目标，直到图片就绪，最长到起飞后 1.2 秒（落地后约 0.5 秒）。原来要先等图片最多 1.2 秒才起飞，连真实服务器时这段就是图片下载时间。飞行最后一次读取之后，目标若又移动超过 0.5px，补一段 160ms 的对位。
- **按帧等待：** 路由完成后的等待改为每 16ms 检查一次；稳定性检查改为连续两帧不变（最长 576ms），原来是至少两次 32ms 睡眠。

## 第三轮：淡入期间开始路由（2026-10-12）

之前三种转场都等自己的动画走完才调用真实路由：海报转场等遮罩 210ms 淡入，首页→媒体夹等 410ms 飞出，返回首页等 320ms 缩小。Emby 的页面切换和数据请求因此全部排在动画之后，动画时间白白浪费。现在改为：

- **海报转场：** 点击后第一帧只显示海报抬起与模糊。第二帧在模糊层下面放一张旧页面的清晰定格画面，然后立刻调用路由，让 Emby 在定格画面下切换页面、请求数据。遮罩不透明后撤掉定格画面，之后与原流程一致。
  - 定格画面优先用空闲时预热的快照（原地提升，并隐藏快照里被点的那张海报），否则现场复制。
  - 现场复制如有外部 `<link>` 样式表，最多等 160ms 加载，超时就退回"淡入后再路由"，绝不显示未上样式的页面。
  - 没有预热快照时，路由会等模糊图对旧页面的同步采集完成后再开始，保证采到的仍是旧页面。
- **首页→媒体夹：** 改回在首页副本上飞出（首页现在也会空闲预热快照，点击时通常免复制）。副本盖住真实首页，媒体夹路由在第二帧开始。
- **返回首页：** 路由在第二帧开始，在缩小的副本下进行。如果首页在被遮住时就开始了自己的入场动画，先暂停，揭开时继续。入场关键帧与节奏不变，任何退出路径都会恢复被暂停的动画。

新增三项检查，每一项都在 `dd22e39` 上失败、在本轮通过：
- 海报转场的路由在遮罩仍在淡入时开始，且开始时有不透明的定格画面。
- 首页→媒体夹的路由在副本仍在飞出时开始。
- 返回首页时，被遮住期间开始的首页入场先暂停，揭开后才继续。

## View Transitions 评估

实测 headless Chromium 141 支持 `document.startViewTransition`，Linux 客户端的 QtWebEngine 6.4（Chromium 102）不支持。同文档 View Transitions 从 Chromium 111 起提供，正式包使用的 Qt 6.9（Chromium 130）和 Android 15+ 的 WebView 都在此范围内。

它的优点是浏览器直接把旧画面截成 GPU 纹理，不复制 DOM，也就没有样式表加载、`:root` 替换、画布和视频无法复制等保真问题；共享元素（`view-transition-name`）还能自动算出海报的位置和尺寸变化。

关键限制：在更新回调完成之前，整页暂停渲染。实测回调等待 500ms 期间只出了 1 帧，同期的 WAAPI 动画时间停在 0。

- **海报转场：不适合。** 要让海报自动飞到详情海报，回调必须等详情数据到达、目标渲染出来，期间整屏冻结几百毫秒，比现在"立即响应、路由同时进行"更差。如果回调在路由切换后立刻结束，目标海报还不存在，就只能淡出而不能飞行。两次串联转场会互相打断。现有方案（模糊图或模糊层 + 定格画面 + 提前路由）更合适。
- **首页→媒体夹、返回首页：适合，但收益已经不大。** 回调只需同步调用路由后立即结束，暂停时间约一帧。旧画面的飞出或缩小、新页面的放大入场都能用 `::view-transition-old/new` 伪元素动画实现，可以省掉出场和入场两份 DOM 副本。不过前两轮之后，这两份副本的首帧开销只剩约 15–30ms，基准里也已没有长帧。还需要保留 Qt 6.4 等旧引擎的现有回退，相当于维护两套实现。

建议：海报转场保持现有方案。首页↔媒体夹之后可在 Qt 6.9 / Android 实机测得副本仍有明显开销时，再以功能检测（`'startViewTransition' in document`）加回退的方式单独引入；目前不改。

## 审查修复：副本样式（2026-10-13）

上游审查在 Windows 与 Chromium 上复现了两个问题，这里都已复现并修复：

1. **复制的样式表加载失败被当作成功。** 原来的等待函数把 `error` 和 `load` 一样计数。现在统一由 `copyStyled()` 判断：任一样式表失败、超时或转场被取消，结果都是"未就绪"。
2. **副本在样式表加载完之前就显示。**
   - 预热快照挂到页面后立即标记为可用，点击正好落在样式表加载期间时，会直接显示未上样式的快照。现在快照要等全部样式表加载成功（最多 2.5 秒）才能被点击使用，失败就丢弃。
   - 返回首页和首页→媒体夹的现场副本原来立即显示（2.5.2 起就有这个问题）。现在先保持不可见，真实页面照常显示，最多等 160ms；失败就退回普通淡入。
   - 首页→媒体夹的入场副本、无 Worker 时的模糊副本也做同样处理。失败时分别改为直接淡出遮罩、只显示暗色遮罩。

另外只复制原页面里实际生效的 `<link>`：加载失败、仍在加载或已禁用的样式表本来就不影响原页面，复制它们只会让副本永远等不到就绪。

新增回归（测试服务器支持可选的 `delay` 与响应头，用 `no-store` 迫使副本重新请求样式表）：

- **慢样式表**（120ms）：新建的定格画面等它加载完才显示，路由仍在淡入期间开始；返回首页的现场副本同样等到加载完才显示。
- **首次加载成功、之后 404 的样式表：**
  - 快照不会被启用。
  - 海报转场的定格画面记为 `late`，改为在遮罩不透明后再路由。
  - 返回首页退回普通淡入。
- **全程逐帧检查：** 没有任何一帧显示缺少样式表的副本。

上述快照、定格画面、返回首页、逐帧检查四项都在 `2021be2` 上失败，修复后通过。Chromium 与 Linux 客户端（QtWebEngine 6.4）四个首页夹具通过，Node 单测 45/45 通过。基准中命中缓存的路径不变；没有预热快照时，路由开始最多晚约 25ms（等待样式表），全程没有超过 50ms 的长帧。
