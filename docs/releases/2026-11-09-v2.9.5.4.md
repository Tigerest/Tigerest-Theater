# Tigerest Theater 2.9.5.4 · 启动超时、截图保存与复制给 AI（Windows）

| 平台 | 安装包 | 系统要求 |
| --- | --- | --- |
| Windows 安装版 | [2.9.5.4 EXE][dl-win-exe] | Windows 10 1903+ / Windows 11，x64 |
| Windows 便携版 | [2.9.5.4 ZIP][dl-win-zip] | 同上；完整解压后运行 |
| Android | [2.9.5 APK][dl-android] | Android 15+，arm64-v8a / x86_64 |
| Apple Silicon Mac | [2.9.5.3 DMG][dl-mac] | macOS 26+，M 系列芯片 |
| iPad / iPhone | [2.9.5 IPA][dl-ios] | iPadOS / iOS 26+，须自行签名安装 |
| Apple TV | [2.9.5 IPA][dl-tvos] | tvOS 26+，须为 Apple TV 签名安装 |

本次只发布 Windows（安装版和便携版）。Mac 仍是 2.9.5.3，安装包在 [2.9.5.3 发行页](https://github.com/Tigerest/Tigerest-Theater/releases/tag/v2.9.5.3)；Android、iPhone／iPad 与 Apple TV 仍是 2.9.5，安装包在 [2.9.5 发行页](https://github.com/Tigerest/Tigerest-Theater/releases/tag/v2.9.5)；这些平台的检查更新不会提示这一版。Windows 的 2.9.5、2.9.5.1、2.9.5.2 和 2.9.5.3 检查更新会提示 2.9.5.4。

这一版的问题来自用户发来的故障诊断报告和 GitHub Issue。

## 服务器响应慢时被判为启动超时

- **问题：** 开始播放满 30 秒时报「播放器启动超时（30 秒）」并停止。后台收到的报告里有 14 份是这个问题，全部来自 2.9.5.3。
- **原因：** 这些报告的日志里，播放内核在等服务器返回数据，一次读取就要 15–29 秒；打开视频要读文件头，有时还要跳到文件尾读索引，几次加起来超过 30 秒，就被客户端的启动计时停掉了。日志看不出服务器慢在哪里（硬盘唤醒还是带宽）。
- **修复：** 启动计时放宽到 75 秒。缓存还在增长时继续等，这部分和 2.9.5.3 一样。
- 这一版只是多等一会儿，服务器响应慢这件事本身没有变，开始播放仍可能要等较久。服务器完全不回应时，播放内核在 75 秒内不会自己放弃，要等到 75 秒才报超时（以前是 30 秒）。

## 连续打不开视频时要等到超时才报错

- **问题：** 连着几次打不开视频时（例如服务器地址解析失败），后面的某一次可能没有反应，要等到启动超时才报错。
- **原因：** 这类失败可能 1 毫秒就结束，「开始」和「结束」两个事件被一起交给客户端处理。客户端的播放状态前后都是「出错」，以为没有变化，就没有通知网页里的播放器。
- **修复：** 每次播放结束都会通知网页里的播放器。

## 选择不重试后播放没有收尾

- **问题：** 播放出错时询问是否重试，选择不重试后，Emby 网页的错误处理因为缺少视频地址而抛出内部错误，停止播放的处理被跳过。
- **修复：** 补上 Emby 需要的字段，让它走完停止播放的处理；用户已经回答过，也不再弹第二个错误对话框。

## 弹幕搜不到、加载失败（#32）

- **问题：** 用自己的媒体服务器时弹幕加载不出来：搜索结果为空，哔哩哔哩来源加载失败。
- **原因：** 部分 Windows 自带的 curl 不支持压缩，弹幕插件要求压缩时，请求还没发出就失败了。
- **修复：** 插件先检查 curl 的能力，不支持时不再要求压缩；哔哩哔哩的弹幕内容总是压缩的，改由插件自己解压。
- 大河服务器的 API 额度用完时，提示「大河服务器API额度已耗尽，请明日重试」，不再显示重试倒计时。

## 截图保存不了（#36）

- **问题：** 安装版按 `s` 或从菜单截图时没有任何提示，电脑上也找不到截图。
- **原因：** 没有设置截图目录时，截图写到程序所在的文件夹；装在 `Program Files` 时没有写入权限，失败只记在日志里。
- **修复：** 没有设置截图目录时，截图保存到系统「图片」文件夹里的 Tigerest Theater 文件夹，第一次截图时自动创建。mpv.conf 里设置的 `screenshot-directory` 仍然优先。保存失败时画面上会提示「截图保存失败，请检查截图目录是否可以写入」。

## 「复制给 AI」失败

- **问题：** 有用户报告，mpv.conf 编辑器里的「复制给 AI」复制不了。
- **修复：** 先用系统剪贴板，系统剪贴板不可用时才退回原来的网页方式。这份报告的失败没有在测试电脑上复现。

## 服务器美化脚本遮住界面（#33）

- **问题：** 服务器用 emby-crx 这类脚本改写 Emby 网页后，客户端登录成功就一直转圈、无法点击。
- **原因：** 脚本注入的全屏加载遮罩（`.misty-loading`）要等 Emby 原版首页出现才会移除，本客户端的首页不满足这个条件。
- **修复：** 客户端直接隐藏这个遮罩。这里只处理遮罩，这类脚本的其他美化效果不保证和本客户端的界面兼容。

## 开着 Windows 自动颜色管理时的颜色

- **问题：** Windows 的「自动颜色管理」（ACM）开着时，系统已经按显示器的配置文件校正桌面颜色，mpv 再读取 ICC 配置文件校正一次，颜色被校正两次。
- **修复：** 检测到 ACM 时不再自动读取 ICC 配置文件。打开「用下方高级参数覆盖当前档位」时仍以高级参数为准。

## 音画不同步的诊断数据

- mpv 提示音画不同步时，日志里多记一组数字：音画偏差、显示器帧率、速度修正和丢帧数等，提示当时和 3 秒后各记一次。有用户反馈的音画不同步这一版没有修复，见已知问题。

其他功能与 2.9.5.3 相同。

## 安装

- `TigerestTheater-2.9.5.4-x64.exe`：Windows 安装版；或完整解压 `TigerestTheater-2.9.5.4-x64.zip` 便携版（保留 `data`）。在 2.9.5、2.9.5.1、2.9.5.2 或 2.9.5.3 的更新窗口点「安装更新」会自动关闭、静默安装并重新打开。2.9.4 的检查更新识别不了四段版本号，会先提示 2.9.5，装好后再检查一次就能升到 2.9.5.4，也可以直接运行这一版的安装包；从 2.9.3 及更早版本升级时完全退出客户端后运行安装向导。未做 Authenticode 签名。
- 播放内核和修补版 QtWebEngine 与 2.9.5.1、2.9.5.2、2.9.5.3 相同。播放内核的原始构建产物 `Tigerest-mpv-rife-x64-5122104.zip` 在 [2.9.5.1 发行页](https://github.com/Tigerest/Tigerest-Theater/releases/tag/v2.9.5.1)，修补版 QtWebEngine 的组件包见 [2.9.4 发行页](https://github.com/Tigerest/Tigerest-Theater/releases/tag/v2.9.4)的 `TigerestWebEngine-6.9.3-d3d11.zip`。已安装的 Windows RIFE 扩展可以继续用于 2.9.5.4，不用重新下载。
- `TigerestTheater-2.9.5.4-SHA256SUMS.txt` 校验本页全部文件；`RELEASE-MANIFEST.json` 记录来源提交、内核来源和验证范围。源码：`client-Sources.zip`（全部客户端，标签 `v2.9.5.4` 对应的提交；Windows 安装包从其中的 `544be21` 构建，之后的提交只改文档）。
- 无法访问 GitHub 时，可从[夸克网盘](https://pan.quark.cn/s/88e6f7a795b4)或[百度网盘](https://pan.baidu.com/s/58azzOU4piiB3miyZqA1dig)的 `2.9.5.4` 文件夹下载同样的 Windows 安装包，用 `SHA256SUMS.txt` 校验。

## 验证范围

- **发布构建：** 安装包和便携包从 `544be21`（打开检查更新）构建。完整串行 CTest 124 个目标全部通过（544 秒）。
- **启动超时：** 在真实客户端里用本机的慢速服务试过两种情况：服务器 40 秒后才给第一个字节，40.8 秒开始播放；服务器一直不回应，客户端在 75.0 秒报「播放器启动超时（75 秒）」并询问是否重试。`test_player_lifecycle` 覆盖 75 秒的计时、缓存还在增长时继续等，以及选择不重试时交给 Emby 的内容。报告里真实的慢服务器没有复现，Emby 网页的错误处理只读过代码，没有实际运行。
- **连续失败：** 报告里第二次失败离开始只有 1 毫秒，这个时机在这台电脑上碰不到：没有这项修复的构建连续 12 次解析失败（每次约 40 毫秒）都能上报。新测试 `failureInOneEventBatchIsReported` 把「开始」和「结束」放进同一批事件，直接交给真实的事件处理函数：去掉修复时第二次失败没有上报，恢复后每次都上报。
- **截图：** 在独立配置的真实客户端里，截图保存到了「图片」文件夹里的 Tigerest Theater（测试后已删除）；目录不可写时，日志有失败记录，窗口截图确认画面上出现了提示。
- **「复制给 AI」：** 真实客户端写入系统剪贴板再读回，内容一致（测试后恢复了剪贴板原来的内容）；编辑器的测试确认按钮走系统剪贴板。报告里的失败没有复现。
- **服务器美化脚本：** `test_server_skin_compat_webengine` 在真实客户端的页面里放一个 `.misty-loading` 全屏遮罩：修复前遮罩还显示着，修复后被隐藏，下面的控件能点到。没有连接真实的 emby-crx 服务器。
- **弹幕：** `test_danmaku_http_webengine` 在 mpv 里用本机服务模拟：curl 不支持压缩时不再要求压缩，哔哩哔哩的压缩弹幕能解开；API 额度用完时提示额度耗尽，普通限流仍提示重试时间。没有连接真实的弹幕服务，也没有在 #32 报告者的系统上试过。
- **ACM：** 单元测试用模拟的显示器数据验证判断逻辑，开着 ACM 的真实显示器没有测过。
- **安装包：** 便携包 1534 个文件与暂存目录逐字节一致，OpenSSL、播放内核（两个 DLL 角色是同一份）与修补版 QtWebEngine 的哈希与锁定值一致；和 2.9.5.3 的便携包逐文件比较，只有主程序不同（这一版改动的脚本都编译在主程序里）。程序内的构建号为 `544be214`，构建日期 2026-11-09。
- **便携包试用：** 便携包解压到新文件夹，在没有开发环境的命令行里用独立配置打开一段本机生成的 1080p 视频（文件名含中文），正常开始播放。把音频延迟临时调到 1.2 秒，mpv 提示音画不同步后，日志里当时和 3 秒后各多了一组数字。截图、目录不可写时的失败记录、连续 4 次打不开视频（每次 37–139 毫秒报错）、美化脚本遮罩和系统剪贴板也在这个包上试过，都符合预期。程序日志里没有乱码。
- 测试和试用使用隔离配置、离线夹具、本机服务和本地视频，试用关闭了自动故障报告；没有用真实 Emby 账号登录，也没有在 Emby 服务器上实际播放。生产接口只收到只读请求（检查更新，以及本地播放时弹幕插件的正常查询）。附件哈希以发行页的 `TigerestTheater-2.9.5.4-SHA256SUMS.txt` 和 `RELEASE-MANIFEST.json` 为准。

## 已知问题

- Windows：有用户反馈播放时音画不同步、感觉画面比声音快。这份日志里片源的时间戳正常，同一集在这台电脑上（120 Hz 显示器）没有复现，原因还没查清，这一版没有修复。遇到时可以在设置里把「音画同步模式」改成「跟随音频时钟」试试，下一份诊断报告里会带上音画偏差的数字。
- Windows：不开补帧、使用默认的「显示器重采样」时，部分高刷新率环境下窗口播放仍可能持续卡顿、增加输出丢帧，全屏正常。这个问题仍未修复；遇到时请先全屏播放，见[故障排查](https://github.com/Tigerest/Tigerest-Theater/wiki/Troubleshooting)。
- Windows：窗口播放剩下的抖动主要来自系统合成，和桌面活动有关（例如任务栏时钟显示秒数时，桌面每秒重绘一次）；全屏最平滑。
- Windows：全屏开着弹幕、按音频时钟播放时，10 分钟测试里出现过一次约 0.15 秒不出新画面（随后掉 2 帧），卡在处理弹幕图层的阶段，原因还没查清。
- Windows：2.9.5.1 的高刷新率节奏改进只在一台 4K 240 Hz 显示器和 RTX 4090 上实测，其他刷新率、显示器和显卡还没验证；也还没在 Emby 串流和网页界面下测过节奏。
- 每帧实际时长和容器标的帧率对不上的视频不补帧，保持原帧播放。目前补帧用的是容器标的平均帧率，帧率判定方式还没改。
- 本地播放还不能把文件直接拖进已经打开的窗口（拖到程序图标或快捷方式上可以），也不记录本地文件的续播位置。
- 返回一面这次还没显示过、图片也不在缓存里的海报墙时，服务器要 0.5–0.8 秒才给出目标卡片，转场约在 0.8–0.9 秒结束。
